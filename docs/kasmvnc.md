# KasmVNC — data plane, exposed API surface, configuration, licensing

WaaS serves the official Kasm workspace images (`docker.io/kasmweb/*`)
**without the Kasm Workspaces platform** — WaaS stays the broker. These
images bundle KasmVNC, which broke with RFB and is browser-only (HTTPS
WebSocket on port 6901, self-signed cert, HTTP Basic auth): **guacd
cannot connect to it**, so `kasmvnc` is a separate data plane, exclusive
on a template (see `docs/templates-and-protocols.md`).

**Version**: the kasmweb `1.19.0` images run **KasmVNC 1.5.1**
(`Xvnc KasmVNC 1.5.1.582662953c…`, package `kasmvncserver 1.5.1-1`,
checked on `kasmweb/terminal:1.19.0`); the newest public upstream tag is
`v1.5.0`. The kasmweb.com KasmVNC docs are outdated (they still
describe 1.0.0): the configuration reference is upstream's
[`unix/kasmvnc_defaults.yaml`](https://github.com/kasmtech/KasmVNC/blob/master/unix/kasmvnc_defaults.yaml)
— or, authoritatively for a given image, its own
`/usr/share/kasmvnc/kasmvnc_defaults.yaml`.

## Data plane

The browser renders KasmVNC's own web client in a same-origin iframe;
`wwt/internal/kasm/kasm.go` reverse-proxies everything under
`/kasm/{sessionID}/…` (HTML, assets, the `/websockify` WebSocket) to
the pod's 6901 endpoint. Unlike the guacd path — one WebSocket per
session — the whole client app flows through this handler.

- **Auth**: nothing is proxied before the platform connection JWT is
  validated. The first request carries `?token=…` (the iframe URL); the
  handler answers with a session-scoped cookie whose value IS the JWT
  (stateless, same expiry). The cookie never goes upstream — the
  `Cookie` header is stripped. **Cookie refresh**: a desktop outlives
  the token's TTL (`WAAS_CONNECTION_TOKEN_TTL`, 5 min by default) many
  times over, so the portal mints a fresh token for the open session
  (`POST /api/v1/workspaces/{id}/sessions/{sid}/token`, owner-only,
  grants re-resolved) and hands it to `GET
  /kasm/{sid}/waas/session?token=…`, which validates it exactly like
  any kasm request (signature, session id match, kasmvnc session),
  re-sets the cookie and answers 204 without touching the workspace.
  The pane does this on a timer at half the token's remaining life
  (read from its `exp`), the Files section before each listing and
  upload (see **Portal integration**).
- **Upstream credentials**: the per-workspace `VNC_PW` Secret
  (`waas-kasm-<name>`, generated by the operator) is injected
  server-side as `Authorization: Basic` for user `kasm_user`
  (`kasm.go`, `proxyTo`) — it never reaches the browser. The proxy also
  sets an `Origin` header when absent: KasmVNC's WebSocket handshake
  parser requires one (browsers always send it, health probes don't).
  A WebSocket upgrade whose `Origin` is present but not the request's own
  host is refused with 403 before anything upstream (`sameOrigin`,
  `kasm.go`) — cross-site WebSocket hijacking defence in depth beyond the
  `SameSite=Strict` cookie, covering the desktop stream and the sidecar
  sockets alike.
- **Session end**: `httputil.ReverseProxy` only returns once the
  upgraded WebSocket closes — that return is the session-end signal
  (`EndSession`). The proxy counts live `/websockify` streams per
  session (the client can hold several: multi-monitor `screen.html`
  windows) and ends the session only once the last one has been gone
  for a **30 s reconnect grace** (`reconnectGrace`, `kasm.go`); a new
  stream within it cancels the pending end. This is what lets
  KasmVNC's own auto-reconnect survive a network blip — an ended
  session answers 409 on `ConnectionInfo`. The reconnect needs a valid
  cookie, which the refresh above keeps current for the session's whole
  life; a portal tab that stopped refreshing (closed, frozen) leaves
  the reconnect to fail with 401 past the expiry, and **Retry** opens a
  fresh session. **The grace lives on one wwt replica, in memory**: with
  `wwt.replicas > 1` and no per-session routing affinity, a reconnect
  that lands on a different replica won't cancel the first replica's
  timer — the row ends while the stream is still live. Running more
  than one `wwt` replica requires sticky routing on `/kasm/{sid}`
  (e.g. ingress-nginx's `upstream-hash-by: $request_uri`-style
  hashing). A wwt restart or crash within the grace loses the pending
  end the same way, and the api-server's SessionSweeper is **not** a
  safety net for that: it only reaps sessions whose workspace CR was
  deleted (`session_sweeper.go`), so a lost end leaves the row open —
  blocking idle-suspend — until the workspace itself goes away.
- **Remote workspaces**: kasmvnc is refused there (400) — the kasm
  proxy targets an in-cluster pod, "external machine" semantics has no
  kasm equivalent (`docs/remote-workspaces.md`).

### Upstream TLS posture

The kasmweb images ship `network.ssl.require_ssl: true` with a
**self-signed certificate**, so the proxy's transport skips
verification (`InsecureSkipVerify`, `kasm.go`). The hop is pod-to-pod
inside the cluster and netpol-guarded. Replacing the self-signed cert
with a cert-manager-issued one is a known pending hardening item
(originally "phase 4" of the kasm feasibility plan) — not implemented.
The kasmvnc-sidecar hop (below) is plain HTTP on the same posture: same
pod-to-pod path, same netpol, and it would move to TLS together with
this item.

## Files: the kasmvnc-sidecar (policy-gated file transfer)

Standalone KasmVNC has no upload and its download surfaces bypass every
policy, and the images' own upload service is a closed platform binary
(see **Capabilities vs the Kasm platform**). File transfer on kasmvnc
is therefore a WaaS component: **`kasmvnc-sidecar/`**, a small HTTP server
(stdlib plus `gorilla/websocket` for the audio routes below) the
operator injects as a **sidecar** of every kasmvnc workload
(`operator/internal/controller/kasmvnc_sidecar.go`; the decision and its
trade-offs are ADR 0003, `docs/adr/0003-kasmvnc-sidecar.md`; audio
is ADR 0004). The contract the three modules share — port `4800`, env,
route names, the PulseAudio paths and the audio wire format — lives in
`shared/kasmvncsidecar`.

- **Routes** (relative to the sidecar; the browser reaches them as
  `/kasm/{sid}/waas/files…`): `GET /files?path=<rel>` lists a directory
  (`[{name, dir, size, mtime}]`, directories first; a symlink reads as
  its target, so a linked directory browses as one, and a link `os.Root`
  refuses — escaping the home, or with an absolute target — is left out
  of the listing), `GET
  /files/download?path=<rel>` streams a file as an inert attachment
  (`application/octet-stream`, `nosniff`, `Content-Security-Policy:
  sandbox`; anything but a regular file — a directory, a FIFO — is 400,
  and the open is non-blocking so a FIFO cannot hang the sidecar), `POST
  /files/upload?dir=<rel>` takes a
  `multipart/form-data` body, streams each part into `dir` (default
  `Uploads`, created if missing) and answers `{"stored": [names]}`.
  Nothing else: no delete, rename or move. **Statuses**: 404 missing,
  403 permission, 413 over the cap, 400 for a path the client named
  that cannot resolve (escaping symlink, a file where a directory was
  expected, a malformed upload body or name), **507** when the home
  volume is full, 500 (logged) for the server's own trouble. There is no
  transaction over the home: a multi-file upload failing mid-way keeps
  the files already stored, and the error body names them (`already
  stored: a.txt, b.pdf`).
- **Gate in wwt** (`fileRouteStatus`, `kasm.go`): after the connection
  JWT is validated like any kasm request, each route is checked against
  the token's `fileTransfer` claims — list needs upload *or* download,
  download its own grant, upload its own — and each route has exactly
  one method (a POST cannot ride a download grant into the upload
  route). 403 otherwise; an unknown path under `/waas` is 404 whatever
  the grant. Only an allowed request is relayed, to
  `http://<workspace service>:4800` with the same injected Basic pair as
  KasmVNC; the sidecar is never addressed by the browser directly. An
  unreachable sidecar answers **503** (the desktop's own failure is 502):
  the sidecar is optional.
- **Auth**: the sidecar accepts the Basic pair wwt already injects
  (`kasm_user:$VNC_PW`, constant-time compare on the password), read
  from the same env entry as the desktop container — the operator
  copies the desktop's `VNC_PW` entry verbatim, whether it is the
  generated Secret's `secretKeyRef` or a template-set value. No new
  secret, nothing to rotate twice; the occupant knowing `VNC_PW` only
  grants them their own home. No `WWW-Authenticate` challenge on 401,
  which through wwt would pop the browser's own login dialog.
- **Confinement**: `os.Root` over `$HOME` — `..`, absolute paths and
  symlinks pointing outside the home are refused by the path resolution
  itself, not by string matching (unit-tested with escaping file and
  directory symlinks). Uploads never overwrite (`report (1).pdf`,
  `report (2).pdf`…), file names are reduced to their base, and a request
  body above the cap is **413** with no truncated file left behind. The
  cap is `operator.kasmvncSidecar.maxUploadSize` (1 GiB default), handed to
  the sidecar as `KASMVNC_SIDECAR_MAX_UPLOAD_BYTES`.
- **Edge body limit**: the upload rides the public edge first, which
  has its own cap — ingress-nginx cuts request bodies at **1m** by
  default and spools them to disk. The chart's Ingress therefore sets
  `nginx.ingress.kubernetes.io/proxy-body-size` from the same value (the
  quantity's binary suffix becomes nginx's: `1Gi` → `1g`, hence "an
  integer with a binary suffix" in the value's doc) and turns
  `proxy-request-buffering` off; one Ingress, so both apply to every
  path. Another ingress controller needs its equivalent raised to the
  cap by hand (the chart only knows nginx's annotations). The Gateway
  API `HTTPRoute` has no body-size limit of its own — whether the
  Gateway implementation adds one is its configuration, not the
  route's.
- **Pod shape**: the sidecar mounts the **same home volume at the same
  path**, read-write, plus the small `waas-pulse` Memory emptyDir it
  shares with the desktop (**Audio** below), and runs as the desktop's
  uid/gid — the container `securityContext` wins over the pod's, else
  the kasmweb `1000/1000` — so uploads land owned by the session user
  and the PulseAudio socket is reachable. Hardened: non-root (unless
  the desktop itself runs as root), read-only rootfs, drop ALL, no
  privilege escalation, RuntimeDefault seccomp; 20m/32Mi requests,
  500m CPU / 128Mi memory limits (uploads stream straight to disk,
  nothing is spooled; PulseAudio and one `parec` per playback stream
  are the footprint — 500m leaves headroom for the daemon plus up to 4
  concurrent `/audio` connections). The CPU limit is load-bearing, not
  just hardening: a policy's `limits.aggregate` renders a `waas-quota`
  namespace `ResourceQuota` with `limits.cpu`/`limits.memory`
  (`operator/internal/controller/placement.go`), and Kubernetes rejects
  any container missing a CPU limit once that scope exists — every
  non-admin kasmvnc workspace stayed `Provisioning` without it. The
  same numbers feed the quota pre-check (`operator/pkg/policy.LoadOf`
  adds the sidecar's footprint to a kasmvnc workspace's load, shared
  via `shared/kasmvncsidecar` so the pod spec and the quota math agree);
  TCP readiness probe on 4800. The workspace Service gains a `waas-files`
  port (converges on every reconcile, ADR 0001's exception). Sidecar
  image: `<registry>/kasmvnc-sidecar:<tag>`, same tag as the other
  components; `operator.kasmvncSidecar.enabled: false` renders an empty
  image, which is the operator's off switch (no sidecar, no port, 503
  from wwt). A kasm template whose desktop has no `VNC_PW` env (an
  explicit credentials Secret feeding the image some other way) gets no
  sidecar either: one that cannot authenticate would only keep the pod
  from turning Ready.
- **Not mirrored**: the sidecar mounts the home volume and nothing
  else. An admin `volumeMounts` passthrough that mounts another volume
  *under* the home (`~/shared`, `~/data`) is visible to the desktop but
  not to the sidecar: the listing shows an empty directory there, and
  an upload into it lands on the home volume, hidden behind the mount
  in the desktop. Known limitation — mirroring every mount would also
  mirror its secrets and hostPaths into a second container.
- **Upgrade note**: the sidecar is part of the pod template, so **every
  platform release** (its image tag follows the components') and every
  `operator.kasmvncSidecar.maxUploadSize` change (an env value) alters the
  spec: already-running kasmvnc workspaces show `TemplateDrifted` and
  converge at their next scale-up boundary (ADR 0001) — the same
  behavior as enabling the sidecar on an installed platform, where
  until then the Files section says file transfer is not available yet
  and to restart.
- **Portal**: the session menu shows a **Files** section on kasmvnc
  sessions when the capabilities grant at least one direction (hidden
  entirely otherwise — `frontend/src/components/SessionFiles.tsx`): the
  home listing with a breadcrumb, files as plain `<a download>` links on
  the download route when download is granted (locked otherwise), an
  **Upload files…** picker when upload is granted (multiple files, into
  `Uploads`, which the listing then shows). The requests ride the
  session cookie (same origin, `Path=/kasm/{sid}`), which the section
  re-sets from a fresh token **before each listing and each upload**
  (`frontend/src/lib/kasmCookie.ts`, the refresh described under
  **Auth**) — so Files works whether or not the iframe has set the
  cookie yet, and a long upload starts on a fresh token; downloads are
  plain links and ride whatever the pane's timer and the listing left.
  They use a plain `fetch`, not the api client, because a 401 there
  must not sign the user out of the portal and the body is the sidecar's
  own JSON. 403 reads "Denied by your policy", 413 names the cap, 503
  the missing sidecar, 401 (the refresh itself failed: the session
  ended underneath) "Session expired — reopen Files".

This is the **governed path for normal use**: a separate container the
occupant cannot modify enforces the grant for *this* route, and KasmVNC's
own `/api/downloads` and `/Downloads` stay blocked whatever the grant
(one auditable route, no symlinked directory listings). It is not a hard
guarantee against the occupant — the in-container channels below (print
over RFB, their own Xvnc, the screen) are unchanged.

## Audio: playback and microphone (kasmvnc-sidecar)

Standalone KasmVNC has no audio, and the images' audio helpers are closed
platform binaries kept off (**Image side services** below) — with
`KASM_SVC_AUDIO=0` the image starts no PulseAudio of its own either, so
desktop apps have nowhere to play. The sidecar fills both roles (ADR
0004, `docs/adr/0004-kasmvnc-sidecar-audio.md`):

- **Sound server**: the sidecar supervises one `pulseaudio` daemon
  (restarted with backoff if it dies) loading exactly three modules:
  `module-native-protocol-unix` on `/run/waas-pulse/native`,
  `module-null-sink` `waas_out` (s16le 48 kHz stereo, the default sink)
  and `module-pipe-source` `waas_mic` (a FIFO at
  `/run/waas-pulse/mic.fifo`, s16le 48 kHz mono, the default source).
  `/run/waas-pulse` is a Memory emptyDir (`waas-pulse`, 8Mi) the
  operator mounts in **both** containers; the desktop gets
  `PULSE_SERVER=unix:/run/waas-pulse/native`, an operator-owned env
  stamped with the side-service toggles and refused in templates like
  them (`kasmcfg.ManagedEnv`). Same uid on both sides, so
  `auth-anonymous=1` and no cookie: the pod is the only path to the
  socket. The modules are on the daemon's command line (no script in
  the shared, desktop-writable emptyDir) and `--disallow-module-loading
  --disallow-exit` lock it: from the desktop, `pactl load-module` and
  `pactl exit` are refused — the occupant can only re-route or mute
  their own streams. Verified on `kasmweb/terminal:1.19.0`: `pactl info`
  inside the desktop reports the sidecar's server with
  `waas_out`/`waas_mic` as defaults, `pacat` plays into it,
  `parec --device=@DEFAULT_SOURCE@` records what the portal sends.
- **Routes** (the browser reaches them as `/kasm/{sid}/waas/audio` and
  `/waas/mic`, WebSocket upgrades behind the same Basic pair as the file
  routes): `GET /audio` streams `waas_out.monitor` — one `parec` per
  connection, killed when the socket closes — as raw PCM **s16le 48 kHz
  stereo, 20 ms binary frames** (3840 bytes, ≈1.5 Mbit/s); `GET /mic`
  takes raw PCM **s16le 48 kHz mono** binary frames and writes them into
  the FIFO (≈0.77 Mbit/s at 20 ms frames; a frame the daemon is not
  draining in time is dropped rather than the socket stalled). **One
  microphone writer at a time**: a second `/mic` connection is refused
  with 409 while one is open; a `/mic` frame over 4096 bytes closes the
  socket, an odd-length one is skipped. At most 4 `/audio` connections
  per sidecar (429 past that); a playback client that stops reading is
  dropped after 5 s. 503 when the daemon is down (`/audio` dials its
  socket before upgrading, `/mic` finds no FIFO reader) — the portal
  shows "not available". Raw PCM is a deliberate ceiling — Opus is the
  upgrade path when the bandwidth matters.
- **Gate in wwt** (`agentRouteStatus`, `kasm.go`, the same table as the
  file routes): `/waas/audio` needs the token's `audio.playback`,
  `/waas/mic` its `audio.microphone`, GET only, 403 otherwise; the
  upgrade is relayed through the same `proxyTo` as everything else. The
  audio sockets are **not** desktop streams: they neither keep a
  session alive past its reconnect grace nor end it. The grant is
  checked at the handshake only: an open socket outlives a policy change
  until it closes, like the desktop stream; the portal turns a toggle off
  when a reconnect's capabilities no longer grant it.
- **Policy**: `WorkspacePolicy.audio {playback, microphone}`, default
  deny, resolved for the **connecting** user at `/connect` like
  `fileTransfer` and stamped into the connection token (`audio`) and the
  session capabilities (`audioPlayback`, `microphone`);
  `docs/governance.md` § Audio policy. The chart's default policy grants
  playback only; the admin policies grant both.
- **Portal** (`frontend/src/lib/kasmAudio.ts` + `lib/pcmWorklet.js`): an
  **Audio** section in the kasmvnc session menu with a *Workspace sound*
  toggle and a *Microphone* toggle, each shown only when granted. Each
  link re-sets the session cookie from a fresh token first (like Files),
  opens its WebSocket and an `AudioContext` at 48 kHz: playback feeds an
  `AudioWorklet` player with a drop-oldest jitter buffer (prime 60 ms,
  cap 300 ms); the microphone captures `getUserMedia({channelCount: 1,
  echoCancellation: true})` through a worklet posting 20 ms blocks,
  converted to s16le on the main thread (resampled first if the browser
  refused a 48 kHz context). A link follows the session: a reconnect
  restarts it on the new session id. The worklet is a plain JS file
  shipped as a hashed same-origin asset (`?url&no-inline`), so the
  nginx CSP (`script-src 'self'`) is untouched; the sockets are covered
  by its `connect-src ws(s)://$http_host`. The KasmVNC client posts
  `enable_audio` to its parent on every click in the desktop; the
  playback link uses that user gesture to resume a context the
  browser's autoplay policy kept suspended. Errors are worded: a refused
  capture ("The browser refused microphone access" — permission, no
  device, or no HTTPS: `getUserMedia` needs a secure context, so the
  dev env's 8080 port has no microphone), a stream that stopped (toggle
  again), a sidecar that is not there (restart the workspace).
- **Soft vs governed**, as for files: the grant holds for this path,
  which the occupant cannot modify; the shared emptyDir is theirs too
  (same uid), so they can unplug the socket or feed the FIFO from inside
  their own session — their own audio, nothing more.
- **Not the images' services**: `kasm_audio_out` (MPEG-TS over its own
  WebSocket on 4901/8081) and `kasm_audio_input_server` (4903) stay off;
  the `KASM_SVC_AUDIO*` stamps are unchanged.

## Portal integration

Embedded in an iframe (`window.self !== window.top`, upstream
`isInsideKasmVDI`), the KasmVNC client behaves as a component of the
Kasm platform: it hides its whole control bar (settings, clipboard
panel, fullscreen button — unless `show_control_bar` is passed), drops
its own status notifications, turns its auto-reconnect on (5 retries,
5 s apart) and talks to its parent with `postMessage({action, value})`.
The portal (`frontend/src/components/DesktopPane.tsx`, kasm branch)
therefore provides what is hidden, using these messages — checked
against the client served by `kasmweb/*:1.19.0`
(`/usr/share/kasmvnc/www/assets/ui-*.js`; upstream `app/ui.js`):

| Direction | Message | What the portal does |
|---|---|---|
| client → portal | `connection_state` (`connecting`, `connected`, `reconnecting`, `disconnecting`, `disconnected`) | drives the pane state; `reconnecting` reads as connecting; `disconnected` is final (embedded, the client auto-reconnects whether the close was clean or not, and only sends it once retries are exhausted, on a graceful server notice, or when reconnect is inhibited): the iframe is unmounted and **Retry** opens a fresh session with a fresh token |
| client → portal | `idle_session_timeout` | final as well: sent on the client's own idle timeout **and** when auto-reconnect retries are exhausted (then right after `connection_state: disconnected`, which already ended the session); the client navigates itself to `disconnected.html` 10 s later. Received first, it is the idle timeout: the pane says so ("Disconnected after 20 minutes without activity") instead of the plain "connection closed" |
| client → portal | `clipboardrx` (`value`: text) | desktop → portal clipboard: fills the session menu's manual exchange (and a best-effort `writeText`); dropped unless the session capabilities allow copy |
| client → portal | `enable_audio` (`value`: null) | posted by the client's `_focusCanvas` on every click in the desktop — a user gesture: the playback link (`lib/kasmAudio.ts`) resumes an `AudioContext` the browser's autoplay policy kept suspended; otherwise ignored |
| portal → client | `clipboardsnd` (`value`: text) | manual exchange "Send to workspace"; only posted when the capabilities allow paste (the client applies it only with `clipboard_up`) |
| portal → client | `setvideoquality` (`value`: `1` low, `2` medium — the client default, `3` high, `5` lossless) | session-menu quality presets, applied live; the choice is also handed to the next iframe URL as `video_quality`, so a reconnect keeps it |

- **Security filter**: a message is accepted only when `event.source`
  is that pane's iframe window **and** `event.origin` is the portal's
  origin — another pane, a popup or a foreign origin cannot drive the
  session. The portal posts to its own origin, never `*`. (The 1.5.1
  client does not check who posts to it; upstream master added an
  `event.source === window.parent` check.)
- **Keyboard**: keystrokes inside the iframe never reach the portal
  window. On each iframe load the pane adds a capture-phase `keydown`
  listener on the iframe window that replays the event on the portal
  window; when a portal handler consumes it (`Ctrl+Alt+M`, `Escape`
  closing the menu) it is kept from the desktop. So on kasmvnc the
  overlay shortcut `Ctrl+Alt+M` never reaches the desktop, whereas on
  guac sessions it is forwarded to it as well. The listener dies with
  the iframe document; the next load binds the new one.
- **Cookie refresh**: the pane re-sets the session cookie from a fresh
  token at half the token's remaining life (read from its `exp`, 30 s
  floor) for as long as the session is up — `DesktopPane`, kasm branch,
  through `lib/kasmCookie.ts` — so the client's own auto-reconnect keeps
  authenticating past the connection token's TTL. A failed refresh is
  retried at the next tick; the loop stops with the session.
- **Idle timeout**: the client disconnects after 20 minutes without
  *input* (keyboard, mouse); the portal keeps that default and never
  sends `set_idle_timeout`. `idle_disconnect=0` does not disable it: the
  client falls back to 1200 s. **Retry** opens a fresh session.
- **Fullscreen**: the session menu toggles the Fullscreen API on the
  whole page, not the pane, so the menu stays reachable.
- **Load fallback**: the client reports its own state, so `onLoad` no
  longer means "connected". An iframe page without the client's
  `noVNC_container` element is an error page — wwt refusing the request
  (plain-text `http.Error`: expired token, ended session) or an ingress
  502/503 HTML page — and the pane shows the failure.
- **Not used**: `terminate` (the client's `unload` handler already
  disconnects cleanly when the iframe is unmounted, and a message posted
  right before unmounting would never be processed), `disconnectrx`
  (redundant with `connection_state: disconnected`), `fullscreen`
  (only sent by the hidden control-bar button), the platform's own
  audio messages other than `enable_audio`, statistics, multi-monitor
  and game-mode messages.

## Exposed `/api` surface

Standalone KasmVNC serves an HTTP API under `/api/…` — nine endpoints,
all requiring owner credentials. `kasm_user` **holds the owner role**
on its own session (`.kasmpasswd` carries the `wo` — write + owner —
flags; verified live 2026-07-10), and the proxy injects the Basic pair
on every request, so a WaaS user's browser reaches this API through the
proxy.

| Endpoint | Effect | Proxied? |
|---|---|---|
| `/api/downloads` | Lists + serves files from the session's downloads folder | **Blocked (403)** |
| `/api/clear_clipboard` | Clears the KasmVNC clipboard and the session's X clipboard | Open |
| `/api/get_screenshot` | Screenshot of the current session | Open |
| `/api/create_user`, `/api/update_user`, `/api/remove_user` | Manage the session's user accounts | Open |
| `/api/send_full_frame` | Forces a full frame resend to read-only users | Open |
| `/api/get_bottleneck_stats`, `/api/get_frame_stats` | Session telemetry | Open |

- **`/api/downloads` is blocked** at the proxy (`isDownloadsPath`,
  `kasm.go`) because it is the same session→browser file egress the
  guacd path gates behind `TierPlatform` for
  `enable-sftp`/`enable-drive` ("until the file-transfer feature ships
  with its own policy gate", `operator/pkg/params/params.go`). The
  governed route is the kasmvnc-sidecar (**Files** above), gated on
  `WorkspacePolicy.fileTransfer`; this endpoint stays blocked outright
  whatever the grant, so there is one auditable file route. This closes
  the HTTP route only — casual or accidental egress — not every channel
  (see **File egress is a soft control** below). The path is
  normalized and lowercased before matching so case, trailing-slash,
  dot and double-slash variants can't slip past.
- **`/Downloads/…` is blocked too**, for the same reason: the kasmweb
  images symlink `/usr/share/kasmvnc/www/Downloads/Downloads` to
  `~/Downloads`, and KasmVNC's built-in HTTP server serves its
  `httpd_directory` following symlinks, directory listings included —
  verified on `kasmweb/terminal:1.19.0`: `GET /Downloads/Downloads/`
  lists `~/Downloads` and every file in it downloads with a 200. The
  whole top-level `/downloads` prefix (same normalization) answers 403.
- **The other eight stay open by documented choice**: a WaaS kasmvnc
  session is single-user and self-owned, with no third party to protect
  the user from — they already have the keyboard and screen.
  `get_screenshot` only leaks their own desktop to their own browser;
  `create_user`/`remove_user` only create accounts on a pod for which
  wwt remains the sole entry point, injecting `kasm_user` regardless.
  Blocking them would be defending against the user's own capabilities
  on their own session.

## Capabilities vs the Kasm platform

Verified against upstream docs and maintainer-settled issues
(2026-07-10):

- **Standalone KasmVNC has**: clipboard, dynamic resize, multi-monitor
  (native "Display Manager"), the downloads API above.
- **Audio (playback + mic)**: absent from standalone KasmVNC at every
  version — a Kasm Workspaces (commercial platform) exclusive
  ([kasmtech/KasmVNC#31](https://github.com/kasmtech/KasmVNC/issues/31)).
  WaaS provides both through the kasmvnc-sidecar's own PulseAudio
  (**Audio** above) — never through the images' closed
  `kasm_audio_out` / `kasm_audio_input_server`.
- **Upload (browser → session)**: absent at every scale and not planned
  upstream ([kasmtech/KasmVNC#209](https://github.com/kasmtech/KasmVNC/issues/209)).
  WaaS provides both directions itself, outside KasmVNC, through the
  kasmvnc-sidecar (**Files** above) — never through the images'
  closed `kasm_upload_server`.

### Image side services: forced off

The kasmweb images do ship the platform's side services as closed-source
binaries, and their `vnc_startup.sh` starts each one unless its toggle
is `0`: audio out (`KASM_SVC_AUDIO`, ports 4901/8081, plus the
PulseAudio + ffmpeg pipeline feeding it), audio in
(`KASM_SVC_AUDIO_INPUT`, 4903), uploads (`KASM_SVC_UPLOADS`, 4902,
writing to `~/Uploads`), gamepad (`KASM_SVC_GAMEPAD`, 4904), webcam
(`KASM_SVC_WEBCAM`, 4905, only with `/dev/video0`), printer
(`KASM_SVC_PRINTER`, a `-UnixRelay` on Xvnc + a PDF service) and
smartcard (`KASM_SVC_SMARTCARD`, `pcscd` + a relay). WaaS proxies none
of them — only 6901 goes through `wwt` — yet the namespace
NetworkPolicy is not port-scoped, so each would be an open listener in
the pod. For kasmvnc containers the operator therefore stamps all seven
(single source: `operator/pkg/kasmcfg.SideServiceEnv`), laid over the
template and override env: six to `"0"`, and `KASM_SVC_PRINTER` to
`"1"` only when the owner's policy allows **download** (see **File
transfer, printing, watermark** below), `"0"` otherwise. Verified on
`kasmweb/terminal:1.19.0`: with them off, Xvnc on 6901 is the only
listener. Like the policy-managed keys, a template that sets one would
be silently overridden, so the admission webhook and the api-server
template validation reject them.

**This is default-off hardening, not enforcement against the session
user.** `vnc_startup.sh` sources the user's own, persistent
`$HOME/.bashrc` before starting Xvnc, and the user owns the Xvnc
process itself (same container, same uid) — so a session user can
`export KASM_SVC_PRINTER=1` (or any of the other six) from inside
their own session and restart Xvnc to re-enable it, or start the
binary by hand. The value of the stamp is fewer listeners and fewer
closed-source binaries running **by default**: it shrinks the attack
surface a visitor would find without effort, it does not gate what the
session's own occupant can do inside their own container — nothing
started or configured inside the container can be relied on against
its own occupant. Two consequences of the stamp itself:

- `KASM_SVC_AUDIO=0` also skips the image's `START_PULSEAUDIO` step
  (it is nested in the audio service start), so the image starts no
  PulseAudio of its own; `START_PULSEAUDIO` itself is left alone. The
  desktop's `PULSE_SERVER` — stamped with the toggles, refused in
  templates like them — points its audio clients at the sidecar's
  daemon instead (**Audio** above).
- Printing (PDF to `~/PDF` and a browser download) is the one toggle a
  policy turns on — a **soft gate**, with exactly the limit described
  above: see **File transfer, printing, watermark**.

## Configuration: file hierarchy and the WaaS merge

KasmVNC itself deep-merges three files, key by key, lowest to highest
priority (official reference:
<https://kasmweb.com/kasmvnc/docs/latest/configuration.html> — outdated,
see **Version** above):

1. `/usr/share/kasmvnc/kasmvnc_defaults.yaml` — the full defaults
   shipped by the image (resolution, encoding, SSL, brute-force,
   default DLP block…).
2. `/etc/kasmvnc/kasmvnc.yaml` — system override.
3. `~/.vnc/kasmvnc.yaml` — user override, **where WaaS mounts its
   per-workspace ConfigMap** (single-file subPath; the `.vnc` directory
   itself is an operator-managed emptyDir so it stays writable for
   KasmVNC's runtime artifacts — `self.pem` lives there — whatever uid
   the image runs as).

Because the image's defaults already apply to every key the WaaS file
leaves unspecified (verified live: a partial user file inherits
resolution, encoding, ssl… from `kasmvnc_defaults.yaml`), **WaaS adds
no base/defaults layer of its own** — re-baking those defaults into a
WaaS constant would freeze them against future image versions. What
WaaS writes into `~/.vnc/kasmvnc.yaml` is TWO layers merged
(`operator/internal/controller/kasm_config.go`):

1. the admin's opaque `WorkspaceTemplate.spec.kasmvncConfig`
   (convenience config, every upstream option works), then
2. the keys derived from the owner's `WorkspacePolicy` (the security
   authority) — the clipboard DLP and the watermark text — stamped last.

A content change rolls the workload: subPath mounts never refresh in
place, so the content hash is stamped on the pod template
(`annotationKasmConfigHash`).

The effective merged file is readable by the workspace owner via
`GET /api/v1/workspaces/{id}/kasmvnc-config`.

**The YAML file is what is effective — the image env is not.** The
kasmweb `vnc_startup.sh` passes its env-derived flags to `vncserver`
(`-FrameRate=24 -DynamicQualityMin=4 -DynamicQualityMax=7 -geometry
$VNC_RESOLUTION …`), but `vncserver` then appends the config-derived
flags AFTER them (captured live on `kasmweb/terminal:1.19.0`: `…
-FrameRate=24 … -FrameRate 60 … -DynamicQualityMin 7 …
-DynamicQualityMax 8 … -geometry 1024x768 …`) and Xvnc keeps the last
value. So for every key the YAML covers, `kasmvnc_defaults.yaml` + the
WaaS override decide, and `VNC_RESOLUTION`, `MAX_FRAME_RATE`,
`VNCOPTIONS` are effectively dead. The defaults the template editor
shows are therefore the real effective defaults.

### Template editor: schema-driven, read from the image

`kasmvncConfig` is edited from the admin template editor (shown only
when a `kasmvnc` protocol is present, same guard as the webhook —
`frontend/src/pages/admin/templates/KasmVNCConfigFieldset.tsx`) in
three tabs over the same data, **Essentials | Advanced | YAML**. The
option list is **not maintained by WaaS**: it is the image's own
`kasmvnc_defaults.yaml`, published by the catalog as the per-entry
`kasmvnc` hint (`docs/image-catalog.md` § KasmVNC defaults) and looked
up for the template's image among the admin catalogs
(`DiscoveredImage.kasmvnc`). Flattened to dotted keys
(`frontend/src/lib/kasmvnc.ts`), each key gets its control type from
its default's YAML type (bool → the tri-state of `ParamField`, int →
number, list → comma-separated text, else text), its default as the
"image default" option, and the file's comments as hints. The header
says what was read: *KasmVNC 1.5.1 · N options read from the image*.

- **Essentials**: a fixed table — the only KasmVNC knowledge WaaS
  keeps (`ESSENTIALS` in the fieldset) — mapping everyday controls to
  keys: initial resolution (`desktop.resolution.width`/`.height`), auto
  resize, max frames per second, image quality (a preset writes both
  `rect_encoding_mode.min_quality`/`max_quality`), disconnect after
  inactivity (`user_session.idle_timeout`, **seconds** or `never` —
  checked in 1.5.1's `vncserver`), ignore Num Lock, game mode,
  clipboard max transfer size (both `…clipboard.*.size`, **bytes** or
  `unlimited`). An essential whose key the image lacks is not offered
  (one line says so); with no defaults known (image not catalogued, or
  a catalog predating the field) every essential is offered without
  its image default. Copy/paste and the watermark are one locked row:
  policy-owned.
- **Advanced**: every key of the file, grouped by top-level section,
  searchable (key or hint); modified rows are highlighted. The
  policy-managed keys are locked, from `GET
  /api/v1/meta/kasmvnc-managed-keys` (the dotted form of
  `kasmcfg.ManagedKeyPaths` — the frontend keeps no copy, same
  doctrine as `/meta/override-fields`). Needs the image defaults; says
  so otherwise.
- **YAML**: the raw editor, unchanged.

The YAML text is the single source of truth (it is what the CR
stores): the structured tabs parse it into a tree and write it back on
every edit. Data is never lost across tabs, but a structured edit
re-serializes the whole text — comments and formatting typed in the
YAML tab are dropped — while an override the tabs cannot represent (a
nested list…) round-trips untouched. What is written is every key set
explicitly, even when equal to the image default: the tri-state
**Off** on a key whose default is `false` is a real override,
**Default** is the absence of the key. Values take the YAML type the
key expects (bools from the default's type; a number is written as a
number whatever the default's type, because KasmVNC's scalar keys are
often unions — `never|<seconds>`, `unlimited|<bytes>`, `auto|<n>` —
whose default is the word; a numeric string with a leading zero such
as `0700` stays a string; a list is typed as comma-separated text,
committed item by item). A key whose default is null in the file
(`data_loss_prevention.watermark:` and `keyboard.remap_keys:`, whose
children or list are only in comments) has no shape to offer a control
for: it is not listed in Advanced, YAML tab only.

**Unknown keys are fatal.** KasmVNC 1.5.1's `vncserver` exits 1 on any
config key it does not support (`CheckForUnsupportedConfigKeys`;
verified live on `kasmweb/terminal:1.19.0` — `Unsupported config keys
found: legacy.option`, Xvnc never starts, the container exits). So
overrides whose key the image does not document are listed as a
warning with a **Remove** action; "documented" is a typed default, a
key under a null-valued default (`…watermark.text.template`), or a
leaf name the file only shows commented out (`# session_type:
shared`). The warning does not block the save — the image defaults may
be absent or stale, and the api-server cannot check it without them —
but the workspace would not start. A policy-managed key present in the
YAML (an old or imported template) is listed the same way, with
**Remove**: the api-server refuses the save while it is set. A footer
counts the overrides (a `key:` left without a value is not one) and
offers **Reset all**. A broken or non-mapping YAML blocks the
structured tabs until fixed. The read-only views (connection settings,
session menu, create dialog) keep showing the raw YAML.

### Clipboard enforcement (policy-derived DLP)

Denying clipboard in the policy actually disables copy/paste inside the
container — not just a greyed-out button. At reconcile, the operator
resolves the workspace **owner's** policy (container-level DLP can only
enforce one policy per workload; on personal kasmvnc namespaces owner
== user; resolution failure fails closed) and stamps three keys, the
single source being `operator/pkg/kasmcfg` (`KeyClipboardCopy`,
`KeyClipboardPaste`, `KeyClientOverride`; `ManagedKeyPaths` is the
union with the watermark keys below):

```yaml
data_loss_prevention.clipboard.server_to_client.enabled: <copyAllowed>
data_loss_prevention.clipboard.client_to_server.enabled: <pasteAllowed>
runtime_configuration.allow_client_to_override_kasm_server_settings: false
```

The third key is always forced off — without it the KasmVNC client can
re-enable the clipboard at connect time (the official docs are explicit
about this). Because the controller overwrites these keys, a template
that sets any of them by hand would be silently ignored — so both the
admission webhook (`workspacetemplate_webhook.go`) and the api-server
template validation (`template_service.go`, mirrored as a clean 400)
reject them, pointing the admin at `WorkspacePolicy.Clipboard`. The
unmanaged clipboard sub-keys (`size`, `allow_mimetypes`,
`delay_between_operations`, `primary_clipboard_enabled`) remain the
admin's. Full precedence map across both data planes:
`docs/clipboard.md`.

This holds against the vector it is built for — the KasmVNC web
client re-enabling the clipboard at connect time, which the third key
above closes. It has the same limit as the side-service stamp above,
though: Xvnc is what enforces the DLP, and the session's own occupant
owns the Xvnc process in their own container — they can kill and
restart it with a different config, bypassing `~/.vnc/kasmvnc.yaml`
altogether. Nothing enforced inside the container by Xvnc or
`vnc_startup.sh` holds against that container's own occupant; it is
the same reasoning as the side services above.

**File egress is a soft control on kasmvnc.** The wwt path blocks
(`/api/downloads`, `/Downloads`) only stop the HTTP routes, i.e.
casual or accidental egress. A determined occupant has other channels
wwt cannot tell apart from the session itself: print jobs travel
inside the RFB WebSocket (UnixRelay messages 182/183,
`common/rfb/msgTypes.h`), not over `/Downloads`; they can restart Xvnc
with their own `-httpd` directory and serve their own client JS; and
the screen itself is an egress channel. The governed path for normal
users is the policy-gated kasmvnc-sidecar (**Files** above) — a
separate container the occupant cannot modify — not a hard guarantee
against the occupant.

### File transfer, printing, watermark (policy gates)

Two more `WorkspacePolicy` fields reach the kasmvnc container through
the **same owner-policy path** as the clipboard (`kasmPolicyOf` →
`applyPolicy`/`desktopEnv`, `operator/internal/controller/kasm_config.go`;
`docs/governance.md` for the fields themselves). One resolution per
reconcile yields the clipboard DLP, the printer toggle and the
rendered watermark; a resolution failure (no user policy) fails closed
on all three — clipboard off, no printing, **no watermark** (there is
no safe text to invent; the deterrent is the permissive side, the hard
gates are what fail closed). A policy spec edit re-enqueues every workspace
of the namespace (the winning policy is a namespace-global
resolution): the reconciler re-renders the `kasmvnc.yaml` ConfigMap and
the pod template (env such as `KASM_SVC_PRINTER`, the config hash)
right away, but — like any pod-template change — a RUNNING workload
only picks it up at its next scale-up boundary or a manual reload, not
mid-session (ADR 0001); until then it shows `TemplateDrifted=True` and
the portal's "update pending" badge.

- **`fileTransfer.upload` / `.download`** — default **deny** (absent =
  false). The api-server resolves the **connecting** user's policy at
  `/connect` and stamps the grant into the connection token
  (`ConnectionClaims.FileTransfer`) and the session capabilities
  (`fileUpload`/`fileDownload`), next to the clipboard. wwt enforces it
  on the kasmvnc-sidecar routes (**Files** above); `/api/downloads` and
  `/Downloads` stay blocked at the proxy regardless, and the guacd
  sftp/drive params stay platform-blocked (no guacd route reads the
  grant).
- **Printing** — `KASM_SVC_PRINTER` is `"1"` when the **owner's** policy
  allows `download` (print-to-PDF then a browser download: the same
  egress class), `"0"` otherwise, inside the `SideServiceEnv` stamp.
  The image then passes `-UnixRelay printer:/tmp/printer` to Xvnc and
  the web client handles the print job over the VNC stream — not over
  `/Downloads`, so the wwt path blocks never see it. **Soft gate**: it
  is a container env toggle, with the limit described above — the
  occupant can set it themselves and restart Xvnc. Default-off stays
  the value.
- **Watermark** — `WorkspacePolicy.watermark` is a text template; when
  set, the operator stamps **one key**,
  `data_loss_prevention.watermark.text.template`, into the policy layer
  (`kasmcfg.KeyWatermarkText`). Nothing else is needed on 1.5.1: font,
  size (48), tint, angle and offset all have Xvnc defaults — verified
  live on `kasmweb/terminal:1.19.0` with only that key in
  `~/.vnc/kasmvnc.yaml`: Xvnc starts with `-DLP_WatermarkText 'WaaS
  alice.smith %H:%M'` on its command line (checked with `ps -eo args`).
  The admin may still tune the other sub-keys (`font_size`, `angle`,
  `timezone_name`…) in `kasmvncConfig`; `…watermark.image` is refused
  there like the text key, because `vncserver` exits when image and
  text are both set — a template image would turn a policy watermark
  into a crash loop. Template syntax: Xvnc runs `strftime` on the text
  live (`%H:%M`, `%Y-%m-%d`), and the WaaS token **`{user}`** is
  replaced by the workspace **owner's** username at reconcile.
  **Escaping**: `vncserver` splices `${NAME}` from its own environment
  into the value, then hands it to Xvnc inside single quotes *without*
  escaping (`-DLP_WatermarkText '<text>'`, through a shell). So a `'`
  breaks out of the argument, and so does any `${…}`: an env value
  (settable through the template or override `env`) can carry a quote
  and run a command, and `${VNC_PW}` would draw the password on
  screen. The CRD therefore refuses `'`, `$` and control characters
  (pattern `^[^'$\x00-\x1f\x7f]*$`, at most 200 characters; the admin
  API mirrors both as a 400 via `kasmcfg.ValidateWatermark`, and the
  operator renders no watermark for a text that fails it). The
  username — the one input an admin does not type — is reduced to
  `[A-Za-z0-9._@-]` (anything else becomes `_`,
  `kasmcfg.WatermarkText`): no quote, `$` or `%` can come from it. A
  text of exactly `true`/`false` renders as `1`/`0` (`vncserver`
  coerces booleans). YAML itself needs no care: the value is
  marshalled, never templated. Soft control like the rest of the file:
  Xvnc renders it, the occupant owns Xvnc.

## Images, placement, licensing

- Catalog entries for `docker.io/kasmweb/*` are approved by **fixed
  release tag** (`tagPolicy: tag`, the bootstrap default in
  `helm/waas/values.yaml`): upstream publishes versioned tags
  (`1.19.0`) and `catalogs/<X.Y>/catalog-kasmweb.yaml` (published by
  `waas-workspace-images` — `docs/image-catalog.md` § Kasm catalog)
  references them by tag. A
  digest requirement was tried first and dropped — it denied every
  entry of the synced catalog (which carries tags, not digests) for no
  real gain; admins who want immutability can still pin `@sha256:…`
  per entry or set `tagPolicy: digest` themselves. Some images are
  multi-arch
  (`core-ubuntu-*`, `ubuntu-noble-desktop`, `firefox`, `vs-code`,
  `terminal`), some amd64-only (`desktop`, `chrome`) — the existing
  `Architectures` → nodeAffinity placement covers this.
- Home lives at `/home/kasm-user` (template `homeMountPath`; the admin
  template editor pre-fills it when kasmvnc is added and the field is
  still empty). `KASMVNC_AUTO_RECOVER=true` comes from the image's own
  env (not from WaaS): `vnc_startup.sh` then restarts a crashed Xvnc in
  place instead of exiting the container.
- **`/dev/shm` is operator-managed**: browsers in kasmweb images outgrow
  the container runtime's default 64Mi, so every kasmvnc pod gets a
  `medium: Memory` emptyDir (`kasmvnc-shm`, `sizeLimit: 512Mi` — enough
  for Firefox/Chrome) mounted at `/dev/shm`. It counts against the
  container's memory limit. A template whose `volumes` passthrough
  already mounts `/dev/shm` keeps its own (sized as the admin wants)
  and gets no second one.
- **Upgrade note**: the side-service env stamps and the `/dev/shm`
  mount are both pod-template changes. Upgrading the operator to a
  version that adds them makes every already-running kasmvnc workspace
  show drift (`TemplateDrifted`); it converges at the workspace's next
  scale-up boundary, not immediately (ADR 0001,
  `docs/adr/0001-template-boundary-convergence.md`).
- **KasmVNC is GPL-2.0**: unlimited execution, including commercial —
  GPL only restricts distribution. WaaS neither redistributes nor
  modifies the images, so no source obligation attaches. The
  `workspaces-images` Dockerfile repos are MIT (covering only the
  Dockerfiles, not the embedded dependencies): pulling from Docker Hub
  is fine, public republication of built images is to avoid (GPL +
  Ubuntu + app EULAs aggregate). The Kasm Workspaces platform is
  proprietary — **never install a Kasm agent** (what provides
  audio/upload): that is what would fall under their license. The
  standalone server has no platform dependency or phone-home.
