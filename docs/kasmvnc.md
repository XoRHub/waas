# KasmVNC — data plane, exposed API surface, configuration, licensing

WaaS serves the official Kasm workspace images (`docker.io/kasmweb/*`)
**without the Kasm Workspaces platform** — WaaS stays the broker. These
images bundle KasmVNC, which broke with RFB and is browser-only (HTTPS
WebSocket on port 6901, self-signed cert, HTTP Basic auth): **guacd
cannot connect to it**, so `kasmvnc` is a separate data plane, exclusive
on a template (see `docs/templates-and-protocols.md`).

**Version**: the kasmweb `1.19.0` images run **KasmVNC 1.5.1**
(`Xvnc KasmVNC 1.5.1.582662953c…`, package `kasmvncserver 1.5.1-1`,
checked on `kasmweb/terminal:1.19.0`); the newest public upstream tag is
`v1.5.0`. The kasmweb.com KasmVNC docs are outdated (they still
describe 1.0.0): the configuration reference is upstream's
[`unix/kasmvnc_defaults.yaml`](https://github.com/kasmtech/KasmVNC/blob/master/unix/kasmvnc_defaults.yaml)
— or, authoritatively for a given image, its own
`/usr/share/kasmvnc/kasmvnc_defaults.yaml`.

## Data plane

The browser renders KasmVNC's own web client in a same-origin iframe;
`wwt/internal/kasm/kasm.go` reverse-proxies everything under
`/kasm/{sessionID}/…` (HTML, assets, the `/websockify` WebSocket) to
the pod's 6901 endpoint. Unlike the guacd path — one WebSocket per
session — the whole client app flows through this handler.

- **Auth**: nothing is proxied before the platform connection JWT is
  validated. The first request carries `?token=…` (the iframe URL); the
  handler answers with a session-scoped cookie whose value IS the JWT
  (stateless, same expiry). The cookie never goes upstream — the
  `Cookie` header is stripped.
- **Upstream credentials**: the per-workspace `VNC_PW` Secret
  (`waas-kasm-<name>`, generated by the operator) is injected
  server-side as `Authorization: Basic` for user `kasm_user`
  (`kasm.go`, `proxyTo`) — it never reaches the browser. The proxy also
  sets an `Origin` header when absent: KasmVNC's WebSocket handshake
  parser requires one (browsers always send it, health probes don't).
- **Session end**: `httputil.ReverseProxy` only returns once the
  upgraded WebSocket closes — that return is the session-end signal
  (`EndSession`). The proxy counts live `/websockify` streams per
  session (the client can hold several: multi-monitor `screen.html`
  windows) and ends the session only once the last one has been gone
  for a **30 s reconnect grace** (`reconnectGrace`, `kasm.go`); a new
  stream within it cancels the pending end. This is what lets
  KasmVNC's own auto-reconnect survive a network blip — an ended
  session answers 409 on `ConnectionInfo`. The reconnect still needs a
  valid cookie: past the connection JWT's expiry (5 min by default) it
  fails with 401 until the portal reopens the iframe with a fresh
  token (the **Retry** button on the disconnected screen — see
  **Portal integration** below). **The grace lives on one wwt replica, in memory**: with
  `wwt.replicas > 1` and no per-session routing affinity, a reconnect
  that lands on a different replica won't cancel the first replica's
  timer — the row ends while the stream is still live. Running more
  than one `wwt` replica requires sticky routing on `/kasm/{sid}`
  (e.g. ingress-nginx's `upstream-hash-by: $request_uri`-style
  hashing). A wwt restart or crash within the grace loses the pending
  end the same way, and the api-server's SessionSweeper is **not** a
  safety net for that: it only reaps sessions whose workspace CR was
  deleted (`session_sweeper.go`), so a lost end leaves the row open —
  blocking idle-suspend — until the workspace itself goes away.
- **Remote workspaces**: kasmvnc is refused there (400) — the kasm
  proxy targets an in-cluster pod, "external machine" semantics has no
  kasm equivalent (`docs/remote-workspaces.md`).

### Upstream TLS posture

The kasmweb images ship `network.ssl.require_ssl: true` with a
**self-signed certificate**, so the proxy's transport skips
verification (`InsecureSkipVerify`, `kasm.go`). The hop is pod-to-pod
inside the cluster and netpol-guarded. Replacing the self-signed cert
with a cert-manager-issued one is a known pending hardening item
(originally "phase 4" of the kasm feasibility plan) — not implemented.

## Portal integration

Embedded in an iframe (`window.self !== window.top`, upstream
`isInsideKasmVDI`), the KasmVNC client behaves as a component of the
Kasm platform: it hides its whole control bar (settings, clipboard
panel, fullscreen button — unless `show_control_bar` is passed), drops
its own status notifications, turns its auto-reconnect on (5 retries,
5 s apart) and talks to its parent with `postMessage({action, value})`.
The portal (`frontend/src/components/DesktopPane.tsx`, kasm branch)
therefore provides what is hidden, using these messages — checked
against the client served by `kasmweb/*:1.19.0`
(`/usr/share/kasmvnc/www/assets/ui-*.js`; upstream `app/ui.js`):

| Direction | Message | What the portal does |
|---|---|---|
| client → portal | `connection_state` (`connecting`, `connected`, `reconnecting`, `disconnecting`, `disconnected`) | drives the pane state; `reconnecting` reads as connecting; `disconnected` is final (embedded, the client auto-reconnects whether the close was clean or not, and only sends it once retries are exhausted, on a graceful server notice, or when reconnect is inhibited): the iframe is unmounted and **Retry** opens a fresh session with a fresh token |
| client → portal | `idle_session_timeout` | final as well: sent on the client's own idle timeout **and** when auto-reconnect retries are exhausted (then right after `connection_state: disconnected`, which already ended the session); the client navigates itself to `disconnected.html` 10 s later. Received first, it is the idle timeout: the pane says so ("Disconnected after 20 minutes without activity") instead of the plain "connection closed" |
| client → portal | `clipboardrx` (`value`: text) | desktop → portal clipboard: fills the session menu's manual exchange (and a best-effort `writeText`); dropped unless the session capabilities allow copy |
| portal → client | `clipboardsnd` (`value`: text) | manual exchange "Send to workspace"; only posted when the capabilities allow paste (the client applies it only with `clipboard_up`) |
| portal → client | `setvideoquality` (`value`: `1` low, `2` medium — the client default, `3` high, `5` lossless) | session-menu quality presets, applied live; the choice is also handed to the next iframe URL as `video_quality`, so a reconnect keeps it |

- **Security filter**: a message is accepted only when `event.source`
  is that pane's iframe window **and** `event.origin` is the portal's
  origin — another pane, a popup or a foreign origin cannot drive the
  session. The portal posts to its own origin, never `*`. (The 1.5.1
  client does not check who posts to it; upstream master added an
  `event.source === window.parent` check.)
- **Keyboard**: keystrokes inside the iframe never reach the portal
  window. On each iframe load the pane adds a capture-phase `keydown`
  listener on the iframe window that replays the event on the portal
  window; when a portal handler consumes it (`Ctrl+Alt+M`, `Escape`
  closing the menu) it is kept from the desktop. So on kasmvnc the
  overlay shortcut `Ctrl+Alt+M` never reaches the desktop, whereas on
  guac sessions it is forwarded to it as well. The listener dies with
  the iframe document; the next load binds the new one.
- **Idle timeout**: the client disconnects after 20 minutes without
  *input* (keyboard, mouse); the portal keeps that default and never
  sends `set_idle_timeout`. `idle_disconnect=0` does not disable it: the
  client falls back to 1200 s. **Retry** opens a fresh session.
- **Fullscreen**: the session menu toggles the Fullscreen API on the
  whole page, not the pane, so the menu stays reachable.
- **Load fallback**: the client reports its own state, so `onLoad` no
  longer means "connected". An iframe page without the client's
  `noVNC_container` element is an error page — wwt refusing the request
  (plain-text `http.Error`: expired token, ended session) or an ingress
  502/503 HTML page — and the pane shows the failure.
- **Not used**: `terminate` (the client's `unload` handler already
  disconnects cleanly when the iframe is unmounted, and a message posted
  right before unmounting would never be processed), `disconnectrx`
  (redundant with `connection_state: disconnected`), `fullscreen`
  (only sent by the hidden control-bar button), audio, statistics,
  multi-monitor and game-mode messages.

## Exposed `/api` surface

Standalone KasmVNC serves an HTTP API under `/api/…` — nine endpoints,
all requiring owner credentials. `kasm_user` **holds the owner role**
on its own session (`.kasmpasswd` carries the `wo` — write + owner —
flags; verified live 2026-07-10), and the proxy injects the Basic pair
on every request, so a WaaS user's browser reaches this API through the
proxy.

| Endpoint | Effect | Proxied? |
|---|---|---|
| `/api/downloads` | Lists + serves files from the session's downloads folder | **Blocked (403)** |
| `/api/clear_clipboard` | Clears the KasmVNC clipboard and the session's X clipboard | Open |
| `/api/get_screenshot` | Screenshot of the current session | Open |
| `/api/create_user`, `/api/update_user`, `/api/remove_user` | Manage the session's user accounts | Open |
| `/api/send_full_frame` | Forces a full frame resend to read-only users | Open |
| `/api/get_bottleneck_stats`, `/api/get_frame_stats` | Session telemetry | Open |

- **`/api/downloads` is blocked** at the proxy (`isDownloadsPath`,
  `kasm.go`) because it is the same session→browser file egress the
  guacd path gates behind `TierPlatform` for
  `enable-sftp`/`enable-drive` ("until the file-transfer feature ships
  with its own policy gate", `operator/pkg/params/params.go`). No such
  gate exists for kasmvnc yet, so the endpoint is blocked outright to
  keep file egress governed identically across protocols. The path is
  normalized and lowercased before matching so case, trailing-slash,
  dot and double-slash variants can't slip past.
- **`/Downloads/…` is blocked too**, for the same reason: the kasmweb
  images symlink `/usr/share/kasmvnc/www/Downloads/Downloads` to
  `~/Downloads`, and KasmVNC's built-in HTTP server serves its
  `httpd_directory` following symlinks, directory listings included —
  verified on `kasmweb/terminal:1.19.0`: `GET /Downloads/Downloads/`
  lists `~/Downloads` and every file in it downloads with a 200. The
  whole top-level `/downloads` prefix (same normalization) answers 403.
- **The other eight stay open by documented choice**: a WaaS kasmvnc
  session is single-user and self-owned, with no third party to protect
  the user from — they already have the keyboard and screen.
  `get_screenshot` only leaks their own desktop to their own browser;
  `create_user`/`remove_user` only create accounts on a pod for which
  wwt remains the sole entry point, injecting `kasm_user` regardless.
  Blocking them would be defending against the user's own capabilities
  on their own session.

## Capabilities vs the Kasm platform

Verified against upstream docs and maintainer-settled issues
(2026-07-10):

- **Standalone KasmVNC has**: clipboard, dynamic resize, multi-monitor
  (native "Display Manager"), the downloads API above.
- **Audio (playback + mic)**: absent from standalone KasmVNC at every
  version — a Kasm Workspaces (commercial platform) exclusive
  ([kasmtech/KasmVNC#31](https://github.com/kasmtech/KasmVNC/issues/31)).
- **Upload (browser → session)**: absent at every scale and not planned
  upstream ([kasmtech/KasmVNC#209](https://github.com/kasmtech/KasmVNC/issues/209)).

### Image side services: forced off

The kasmweb images do ship the platform's side services as closed-source
binaries, and their `vnc_startup.sh` starts each one unless its toggle
is `0`: audio out (`KASM_SVC_AUDIO`, ports 4901/8081, plus the
PulseAudio + ffmpeg pipeline feeding it), audio in
(`KASM_SVC_AUDIO_INPUT`, 4903), uploads (`KASM_SVC_UPLOADS`, 4902,
writing to `~/Uploads`), gamepad (`KASM_SVC_GAMEPAD`, 4904), webcam
(`KASM_SVC_WEBCAM`, 4905, only with `/dev/video0`), printer
(`KASM_SVC_PRINTER`, a `-UnixRelay` on Xvnc + a PDF service) and
smartcard (`KASM_SVC_SMARTCARD`, `pcscd` + a relay). WaaS proxies none
of them — only 6901 goes through `wwt` — yet the namespace
NetworkPolicy is not port-scoped, so each would be an open listener in
the pod. For kasmvnc containers the operator therefore sets all seven
to `"0"` (single source: `operator/pkg/kasmcfg.DisabledSideServiceEnv`),
laid over the template and override env; verified on
`kasmweb/terminal:1.19.0`: with them off, Xvnc on 6901 is the only
listener. Like the clipboard keys, a template that sets one would be
silently overridden, so the admission webhook and the api-server
template validation reject them.

**This is default-off hardening, not enforcement against the session
user.** `vnc_startup.sh` sources the user's own, persistent
`$HOME/.bashrc` before starting Xvnc, and the user owns the Xvnc
process itself (same container, same uid) — so a session user can
`export KASM_SVC_PRINTER=1` (or any of the other six) from inside
their own session and restart Xvnc to re-enable it, or start the
binary by hand. The value of the stamp is fewer listeners and fewer
closed-source binaries running **by default**: it shrinks the attack
surface a visitor would find without effort, it does not gate what the
session's own occupant can do inside their own container. The actual
enforced control for session→browser file egress is the wwt-side path
blocks below (`/api/downloads`, `/Downloads`) — nothing started or
configured inside the container can be relied on against its own
occupant. Two consequences of the stamp itself:

- `KASM_SVC_AUDIO=0` also skips the image's `START_PULSEAUDIO` step
  (it is nested in the audio service start), so no PulseAudio runs in
  the pod by default. `START_PULSEAUDIO` itself is left alone.
- Printing (PDF to `~/PDF` and a browser download) defaults off, same
  as every other side service here — not gated: see above.

## Configuration: file hierarchy and the WaaS merge

KasmVNC itself deep-merges three files, key by key, lowest to highest
priority (official reference:
<https://kasmweb.com/kasmvnc/docs/latest/configuration.html> — outdated,
see **Version** above):

1. `/usr/share/kasmvnc/kasmvnc_defaults.yaml` — the full defaults
   shipped by the image (resolution, encoding, SSL, brute-force,
   default DLP block…).
2. `/etc/kasmvnc/kasmvnc.yaml` — system override.
3. `~/.vnc/kasmvnc.yaml` — user override, **where WaaS mounts its
   per-workspace ConfigMap** (single-file subPath; the `.vnc` directory
   itself is an operator-managed emptyDir so it stays writable for
   KasmVNC's runtime artifacts — `self.pem` lives there — whatever uid
   the image runs as).

Because the image's defaults already apply to every key the WaaS file
leaves unspecified (verified live: a partial user file inherits
resolution, encoding, ssl… from `kasmvnc_defaults.yaml`), **WaaS adds
no base/defaults layer of its own** — re-baking those defaults into a
WaaS constant would freeze them against future image versions. What
WaaS writes into `~/.vnc/kasmvnc.yaml` is TWO layers merged
(`operator/internal/controller/kasm_config.go`):

1. the admin's opaque `WorkspaceTemplate.spec.kasmvncConfig`
   (convenience config, every upstream option works), then
2. the clipboard DLP keys derived from `WorkspacePolicy.Clipboard`
   (the security authority), stamped last.

A content change rolls the workload: subPath mounts never refresh in
place, so the content hash is stamped on the pod template
(`annotationKasmConfigHash`).

The effective merged file is readable by the workspace owner via
`GET /api/v1/workspaces/{id}/kasmvnc-config`.

**The YAML file is what is effective — the image env is not.** The
kasmweb `vnc_startup.sh` passes its env-derived flags to `vncserver`
(`-FrameRate=24 -DynamicQualityMin=4 -DynamicQualityMax=7 -geometry
$VNC_RESOLUTION …`), but `vncserver` then appends the config-derived
flags AFTER them (captured live on `kasmweb/terminal:1.19.0`: `…
-FrameRate=24 … -FrameRate 60 … -DynamicQualityMin 7 …
-DynamicQualityMax 8 … -geometry 1024x768 …`) and Xvnc keeps the last
value. So for every key the YAML covers, `kasmvnc_defaults.yaml` + the
WaaS override decide, and `VNC_RESOLUTION`, `MAX_FRAME_RATE`,
`VNCOPTIONS` are effectively dead. The defaults the template editor
shows are therefore the real effective defaults.

### Template editor: schema-driven, read from the image

`kasmvncConfig` is edited from the admin template editor (shown only
when a `kasmvnc` protocol is present, same guard as the webhook —
`frontend/src/pages/admin/templates/KasmVNCConfigFieldset.tsx`) in
three tabs over the same data, **Essentials | Advanced | YAML**. The
option list is **not maintained by WaaS**: it is the image's own
`kasmvnc_defaults.yaml`, published by the catalog as the per-entry
`kasmvnc` hint (`docs/image-catalog.md` § KasmVNC defaults) and looked
up for the template's image among the admin catalogs
(`DiscoveredImage.kasmvnc`). Flattened to dotted keys
(`frontend/src/lib/kasmvnc.ts`), each key gets its control type from
its default's YAML type (bool → the tri-state of `ParamField`, int →
number, list → comma-separated text, else text), its default as the
"image default" option, and the file's comments as hints. The header
says what was read: *KasmVNC 1.5.1 · N options read from the image*.

- **Essentials**: a fixed table — the only KasmVNC knowledge WaaS
  keeps (`ESSENTIALS` in the fieldset) — mapping everyday controls to
  keys: initial resolution (`desktop.resolution.width`/`.height`), auto
  resize, max frames per second, image quality (a preset writes both
  `rect_encoding_mode.min_quality`/`max_quality`), disconnect after
  inactivity (`user_session.idle_timeout`, **seconds** or `never` —
  checked in 1.5.1's `vncserver`), ignore Num Lock, game mode,
  clipboard max transfer size (both `…clipboard.*.size`, **bytes** or
  `unlimited`). An essential whose key the image lacks is not offered
  (one line says so); with no defaults known (image not catalogued, or
  a catalog predating the field) every essential is offered without
  its image default. Copy/paste is a locked row: policy-owned.
- **Advanced**: every key of the file, grouped by top-level section,
  searchable (key or hint); modified rows are highlighted. The
  policy-managed keys are locked, from `GET
  /api/v1/meta/kasmvnc-managed-keys` (the dotted form of
  `kasmcfg.ManagedClipboardKeyPaths` — the frontend keeps no copy, same
  doctrine as `/meta/override-fields`). Needs the image defaults; says
  so otherwise.
- **YAML**: the raw editor, unchanged.

The YAML text is the single source of truth (it is what the CR
stores): the structured tabs parse it into a tree and write it back on
every edit. Data is never lost across tabs, but a structured edit
re-serializes the whole text — comments and formatting typed in the
YAML tab are dropped — while an override the tabs cannot represent (a
nested list…) round-trips untouched. What is written is every key set
explicitly, even when equal to the image default: the tri-state
**Off** on a key whose default is `false` is a real override,
**Default** is the absence of the key. Values take the YAML type the
key expects (bools from the default's type; a number is written as a
number whatever the default's type, because KasmVNC's scalar keys are
often unions — `never|<seconds>`, `unlimited|<bytes>`, `auto|<n>` —
whose default is the word; a numeric string with a leading zero such
as `0700` stays a string; a list is typed as comma-separated text,
committed item by item). A key whose default is null in the file
(`data_loss_prevention.watermark:` and `keyboard.remap_keys:`, whose
children or list are only in comments) has no shape to offer a control
for: it is not listed in Advanced, YAML tab only.

**Unknown keys are fatal.** KasmVNC 1.5.1's `vncserver` exits 1 on any
config key it does not support (`CheckForUnsupportedConfigKeys`;
verified live on `kasmweb/terminal:1.19.0` — `Unsupported config keys
found: legacy.option`, Xvnc never starts, the container exits). So
overrides whose key the image does not document are listed as a
warning with a **Remove** action; "documented" is a typed default, a
key under a null-valued default (`…watermark.text.template`), or a
leaf name the file only shows commented out (`# session_type:
shared`). The warning does not block the save — the image defaults may
be absent or stale, and the api-server cannot check it without them —
but the workspace would not start. A policy-managed key present in the
YAML (an old or imported template) is listed the same way, with
**Remove**: the api-server refuses the save while it is set. A footer
counts the overrides (a `key:` left without a value is not one) and
offers **Reset all**. A broken or non-mapping YAML blocks the
structured tabs until fixed. The read-only views (connection settings,
session menu, create dialog) keep showing the raw YAML.

### Clipboard enforcement (policy-derived DLP)

Denying clipboard in the policy actually disables copy/paste inside the
container — not just a greyed-out button. At reconcile, the operator
resolves the workspace **owner's** policy (container-level DLP can only
enforce one policy per workload; on personal kasmvnc namespaces owner
== user; resolution failure fails closed) and stamps three keys, the
single source being `operator/pkg/kasmcfg.ManagedClipboardKeyPaths`:

```yaml
data_loss_prevention.clipboard.server_to_client.enabled: <copyAllowed>
data_loss_prevention.clipboard.client_to_server.enabled: <pasteAllowed>
runtime_configuration.allow_client_to_override_kasm_server_settings: false
```

The third key is always forced off — without it the KasmVNC client can
re-enable the clipboard at connect time (the official docs are explicit
about this). Because the controller overwrites these keys, a template
that sets any of them by hand would be silently ignored — so both the
admission webhook (`workspacetemplate_webhook.go`) and the api-server
template validation (`template_service.go`, mirrored as a clean 400)
reject them, pointing the admin at `WorkspacePolicy.Clipboard`. The
unmanaged clipboard sub-keys (`size`, `allow_mimetypes`,
`delay_between_operations`, `primary_clipboard_enabled`) remain the
admin's. Full precedence map across both data planes:
`docs/clipboard.md`.

This holds against the vector it is built for — the KasmVNC web
client re-enabling the clipboard at connect time, which the third key
above closes. It has the same limit as the side-service stamp above,
though: Xvnc is what enforces the DLP, and the session's own occupant
owns the Xvnc process in their own container — they can kill and
restart it with a different config, bypassing `~/.vnc/kasmvnc.yaml`
altogether. Nothing enforced inside the container by Xvnc or
`vnc_startup.sh` holds against that container's own occupant; it is
the same reasoning as the side services above, and the same reason the
hard file-egress controls live in `wwt`, not in the container.

## Images, placement, licensing

- Catalog entries for `docker.io/kasmweb/*` are approved by **fixed
  release tag** (`tagPolicy: tag`, the bootstrap default in
  `helm/waas/values.yaml`): upstream publishes versioned tags
  (`1.19.0`) and `catalogs/<X.Y>/catalog-kasmweb.yaml` (published by
  `waas-workspace-images` — `docs/image-catalog.md` § Kasm catalog)
  references them by tag. A
  digest requirement was tried first and dropped — it denied every
  entry of the synced catalog (which carries tags, not digests) for no
  real gain; admins who want immutability can still pin `@sha256:…`
  per entry or set `tagPolicy: digest` themselves. Some images are
  multi-arch
  (`core-ubuntu-*`, `ubuntu-noble-desktop`, `firefox`, `vs-code`,
  `terminal`), some amd64-only (`desktop`, `chrome`) — the existing
  `Architectures` → nodeAffinity placement covers this.
- Home lives at `/home/kasm-user` (template `homeMountPath`; the admin
  template editor pre-fills it when kasmvnc is added and the field is
  still empty). `KASMVNC_AUTO_RECOVER=true` comes from the image's own
  env (not from WaaS): `vnc_startup.sh` then restarts a crashed Xvnc in
  place instead of exiting the container.
- **`/dev/shm` is operator-managed**: browsers in kasmweb images outgrow
  the container runtime's default 64Mi, so every kasmvnc pod gets a
  `medium: Memory` emptyDir (`kasmvnc-shm`, `sizeLimit: 512Mi` — enough
  for Firefox/Chrome) mounted at `/dev/shm`. It counts against the
  container's memory limit. A template whose `volumes` passthrough
  already mounts `/dev/shm` keeps its own (sized as the admin wants)
  and gets no second one.
- **Upgrade note**: the side-service env stamps and the `/dev/shm`
  mount are both pod-template changes. Upgrading the operator to a
  version that adds them makes every already-running kasmvnc workspace
  show drift (`TemplateDrifted`); it converges at the workspace's next
  scale-up boundary, not immediately (ADR 0001,
  `docs/adr/0001-template-boundary-convergence.md`).
- **KasmVNC is GPL-2.0**: unlimited execution, including commercial —
  GPL only restricts distribution. WaaS neither redistributes nor
  modifies the images, so no source obligation attaches. The
  `workspaces-images` Dockerfile repos are MIT (covering only the
  Dockerfiles, not the embedded dependencies): pulling from Docker Hub
  is fine, public republication of built images is to avoid (GPL +
  Ubuntu + app EULAs aggregate). The Kasm Workspaces platform is
  proprietary — **never install a Kasm agent** (what provides
  audio/upload): that is what would fall under their license. The
  standalone server has no platform dependency or phone-home.
